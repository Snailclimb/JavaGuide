用户已经说过“项目升级到了 Java 21”，换一个会话，Agent 却又给出 Java 8 的配置。这种情况不一定是模型不懂 Java 21，也可能是上次的信息根本没有进入这次请求。

Agent 要复用过去的信息，需要有地方保存它，并在回答相关问题时读出来。当前任务的进展、用户长期使用的技术栈、已经作废的项目约定，保存和使用的方式也不一样。这些就是记忆系统要处理的问题。

滑动窗口和结果卸载涉及上下文容量，具体实现还可以参考 [《上下文工程(Context Engineering) 是什么？和 Prompt Engineering 有什么区别？》](./context-engineering.md)。

## Agent 的记忆系统是如何设计的？

![Agent 记忆分类全景图](https://oss.javaguide.cn/github/javaguide/ai/agent/agent-memory-memory-taxonomy.svg)

记忆系统通常分两层：短期记忆和长期记忆。

短期记忆是 Session 级的，服务当前任务；长期记忆是跨 Session 的，负责把用户偏好、历史决策、过往经验沉淀下来。两者需要区分作用范围和生命周期，但可以共用底层存储，通过会话、用户或命名空间隔离数据。

![AI Agent 记忆系统架构](https://oss.javaguide.cn/github/javaguide/ai/agent/agent-memory-arch.png)

### 记忆有哪些存储形式？

除了按时间维度拆，记忆还可以按存储位置和表征形式分成三类。

| 存储形式     | 说明                                     | 典型实现                          |
| ------------ | ---------------------------------------- | --------------------------------- |
| Token 级记忆 | 以自然语言或离散符号形式存储在外部数据库 | 向量库中的文本块、结构化 JSON     |
| 参数化记忆   | 将信息编码进模型参数中                   | 预训练知识、LoRA 适配器、SFT 微调 |
| 潜在记忆     | 以隐式形式承载在模型内部表示中           | KV Cache、激活值、Hidden States   |

这三种形式可以由同一系统管理。[MemOS 论文](https://arxiv.org/abs/2505.22101)提出用 MemCube 统一描述和管理异构记忆；不同形式之间能否转换，取决于具体策略与运行时支持，不是按使用频率自动升级的存储层级。

### 记忆在功能上如何分类？

按功能目的看，Agent 记忆可以分成三类。

| 功能类型 | 核心问题           | 存储内容                     | 典型场景               |
| -------- | ------------------ | ---------------------------- | ---------------------- |
| 事实记忆 | 智能体知道什么     | 用户偏好、环境状态、显式事实 | 记住用户的技术栈偏好   |
| 经验记忆 | 智能体如何改进     | 过往轨迹、成败教训、策略知识 | 从失败的代码审查中学习 |
| 工作记忆 | 智能体当前思考什么 | 当前推理上下文、任务进展     | 多步推理中的中间状态   |

按内容性质还可以继续细分：

- 情景记忆（Episodic Memory）：记录特定时间、场景下的具体事件，回答 “What happened?”。例如：“上周三用户反馈订单超时问题”。
- 语义记忆（Semantic Memory）：保存事实和概念，也可以从具体事件中归纳知识。例如，结合多次反馈，记录“该用户对性能问题的敏感度高于功能需求”。
- 程序记忆（Procedural Memory）：保存后续执行任务时可以复用的规则和做法。例如：“处理该用户的代码审查时，优先检查 OOM 风险”。规则会影响执行顺序，但不保证 Agent 每次都能正确执行。

### 记忆操作的生命周期是怎样的？

编码和存储解决写入，提取解决读取，巩固、反思和遗忘则处理后续维护。可以按这条链路理解各项操作，但不要求每条记忆都按顺序走完：

![记忆操作的生命周期](https://oss.javaguide.cn/github/javaguide/ai/agent/agent-memory-lifestyle.png)

| 操作 | 说明                               | 工程实现                      |
| ---- | ---------------------------------- | ----------------------------- |
| 编码 | 将原始交互转化为可存储的结构化信息 | LLM 提取事实三元组、生成摘要  |
| 存储 | 将编码后的信息持久化               | 写入向量库 / 图数据库 / 参数  |
| 提取 | 根据上下文检索相关记忆             | 向量检索 + BM25 + 图遍历      |
| 巩固 | 将短期记忆转化为长期记忆           | 异步任务：对话摘要 → 实体库   |
| 反思 | 主动回顾评估记忆内容，优化决策     | 任务完成后提取 Meta-Knowledge |
| 遗忘 | 淘汰低价值或过时记忆               | 权重衰减 + 冲突标记废弃       |

比如“这个项目已经升级到 Java 21”值得保存，“我再想想要不要升级”就不能当成已完成的变更。如果每轮对话都直接入库，这两句话很容易混在一起，后续检索还得重新分辨。

写入前可以用 `importance` 等规则筛选，再由后台任务合并重复记录、处理冲突和过期信息。也有研究用强化学习选择读写时机，不过需要额外的训练和回放，还要能解释为什么保留或丢弃一条信息。业务规则能解决的问题，没有必要一开始就引入这套训练过程。

### 什么是短期记忆（Short-Term Memory / Working Memory）？

短期记忆保存当前会话的状态，包括用户消息、模型回复、工具调用结果，以及任务进行到了哪一步。以 [LangGraph](https://docs.langchain.com/oss/python/concepts/memory#short-term-memory) 为例，这些状态可以通过 checkpointer 持久化，进程重启后仍能恢复。因此，短期记忆中的“短期”说的是会话范围，并不意味着只能放在内存中。

状态里保存了什么，与本轮发给模型什么，需要分开看。历史消息可以先裁剪，工具结果可以只取摘要，`state` JSON 里的控制字段也不必全部放进 Prompt。真正受上下文窗口限制的是最终发给模型的内容。

查询上下文上限时，要看具体的 model ID。例如，[Grok 4](https://x.ai/news/grok-4) 的官方上限是 256K Token，2M Token 对应的是 [Grok 4 Fast](https://x.ai/news/grok-4-fast)。同一个产品家族也可能差很多，选型时应以对应的 model card 或 API 文档为准，并记录核对日期。

**把窗口填满，模型就一定能记住里面的内容吗？**

[《Lost in the Middle》](https://arxiv.org/abs/2307.03172)在多文档问答和键值检索任务中观察到，相关信息放在上下文首尾时，模型往往表现更好；移到中间，效果可能下降。这个结果说明“放得下”和“用得好”有区别，不能据此给所有模型规定一个统一的最佳长度。长输入还会增加处理开销；API 账单则要结合 Token 单价、缓存和长上下文定价来看。

![上下文利用率的 40% 阈值现象](https://oss.javaguide.cn/github/javaguide/ai/harness/context-utilization-40-percent-threshold-phenomenon.svg)

图中的 40% 来自特定模型和任务的观察，不是通用阈值；Lost in the Middle 的位置偏差与上下文增长后信息利用率下降是两件事，不能混为一谈。

控制短期记忆的大小，常用的是缩减、卸载和隔离。三者处理的对象不同。

**上下文缩减（Context Reduction）处理对话历史。** 达到预设 Token 阈值后，可以移除较早的消息，也可以把历史压缩成摘要。前者容易丢掉早期约定，后者可能漏掉版本号、数值等细节；无论选哪种，都要检查当前任务依赖的信息是否还在。

**上下文卸载（Context Offloading）处理体积大的结果。** 工具读到很长的 CSV 后，可以把原始文件留在外部存储，只返回摘要和路径。路径在这里充当后续读取的入口，也可以换成能定位原文的 UUID。Agent 要查看某部分数据，再调用读取工具即可。

卸载之后，读取工具也得配合限制返回大小和超时。如果顺着路径又把整份 CSV 塞回上下文，这次卸载就没有达到控制输入的目的。读取结果被截断时，要说明截断位置，让模型知道自己尚未看到全部数据。

**上下文隔离（Context Isolation）用于拆分子任务。** 分配任务时，主 Agent 给出任务说明和相关材料，子 Agent 在自己的上下文中处理。完整历史不必一并传递：里面与子任务无关的消息会重复消耗 Token，也可能干扰判断。

### 什么是长期记忆（Long-Term Memory）？

“以后代码示例都用 Python + FastAPI”，这句话只留在当前对话里，下次新开会话时模型未必还能看到。要让偏好继续生效，应用需要把它保存到会话之外，再在相关任务中读回来。

**写入（Record）时保存的不只是偏好文字。** 用户标识说明这是谁的偏好，源消息用于核对原意，更新时间则帮助判断记录是否过时。例如“给 CFO 的汇报用非技术化表达”，如果原话只针对本次汇报，就应该连同这个范围一起保存，不能扩展成用户对所有回答的要求。

保存时间可以根据后续任务安排。[LangGraph 的记忆文档](https://docs.langchain.com/oss/python/concepts/memory#writing-memories)提供了两种思路：需要马上用到的新信息，在当前请求中写入；可以稍后整理的内容，交给后台任务。后台抽取尚未结束时，下一次读取当然也就看不到新记录，这段延迟需要由应用处理。

LLM 负责抽取时，不能保证每条有用的信息都被记住，也不能保证它对原话的理解始终正确。这是抽取阶段尽力而为（Best-Effort）的含义。**数据库层面的重复写入则可以通过幂等控制避免。**

比如一次抽取已经写入成功，但调用方没有收到成功响应，于是重试。使用“源消息 ID + 抽取批次 ID”作为幂等 Key，并在重试时复用它，就能识别这是同一批操作。若 Key 来自结果文字的哈希，模型把同一句偏好换个说法，哈希就变了，重复记录仍会写进去。多个会话同时更新一条偏好时，还需要乐观锁等版本检查或事务并发控制，避免较晚完成的旧任务覆盖新值。

**检索（Retrieve）可以在需要记忆的任何一步触发。** 新会话讨论接口实现，就按用户范围取回 Python + FastAPI 偏好；后续任务转到另一个项目，再根据项目范围查询。走向量检索时，相似度只负责找候选，是否过期、是否适用于当前任务，还要检查记录本身。

检索放在生成之前，会增加首 Token 延迟（TTFT）。对少量稳定偏好，可以在会话开始时预加载；反复读取的记录可以用 Redis 缓存；大量历史材料再按查询召回、精排。需要某条记忆才能生成答案，就不能靠把检索放到后台省掉这次等待。并行执行适用于彼此没有依赖的步骤。

### 长期记忆和 RAG 有什么区别？

![长期记忆与 RAG（检索增强生成）的区别](https://oss.javaguide.cn/github/javaguide/ai/agent/agent-memory-rag-vs-memory.svg)

给用户生成接口示例时，Agent 可能同时需要两类信息：接口的字段定义，以及用户偏好的 Python + FastAPI 写法。字段定义可以从公司文档中检索，写法偏好则来自以前的交互。一次回答可以同时用到 RAG 和长期记忆。

**RAG 解决的是从外部知识源取回答案依据。** 公司规章、产品文档和实时数据库查询结果，都可以是知识源。按用户或角色过滤、按偏好重排也可以放进这条流程，所以 RAG 本身并不排斥个性化。

**长期记忆还要管理交互留下的信息怎样变化。** 用户改了技术栈，原来的偏好就不能继续当作当前要求。项目决策可能由多人共同使用，个人偏好通常只属于本人；具体共享到哪里，由命名空间和权限决定。

实现时，可以分别召回外部文档和交互记忆，再统一排序。记忆中的项目名等实体可用于扩展 RAG query，用户偏好可用于重排。存储上是否使用同一套向量库，并不能直接区分两者。

## 主流的记忆技术架构有哪些？

向量化存储、语义检索和记忆管理往往会单独拆出来：主 Agent 负责调度，记忆组件负责写入、查询和维护。

### 底层存储架构通常包含哪些层级？

底层常见的职责可分为三层。

VectorStore 保存记忆对应的向量，并按查询向量取回候选。Pinecone、Weaviate、Chroma、Qdrant 等都能承担这部分工作。延迟还取决于数据量、维度、过滤条件、索引参数和并发，不能只凭产品名或一个 `ef` 值给出 P99 保证。可以参考 [ann-benchmarks.com](https://ann-benchmarks.com/) 或厂商基准的测试方法，再用自己的记忆数据和查询负载比较。

如果问题是“同事 A 负责的项目 B 最近有什么变化”，还需要关联人物、项目和事件。GraphStore 可以用实体和关系保存这些连接，例如通过 Neo4j 沿关系查找；是否需要图存储，取决于查询是否确实依赖关系遍历。

向量检索取回候选后，Reranker 再比较问题与每条记忆的相关性。常见 Cross-Encoder 会联合读取两段文本，因此开销随候选数量和长度增加。它能重排已召回内容，但无法补回候选集里没有的记忆。

向量库选型要同时核对索引、过滤、隔离、一致性和成本：

| 维度         | 关键考量                          | 说明                                   |
| ------------ | --------------------------------- | -------------------------------------- |
| 索引类型     | HNSW / IVF / DiskANN              | 影响召回率与延迟的 tradeoff            |
| 元数据过滤   | pre-filter vs post-filter         | 过滤选择性与索引实现会影响召回率和延迟 |
| 多租户隔离   | Namespace / Collection / 物理隔离 | 影响召回率与数据安全                   |
| 持久化一致性 | 强一致 vs 最终一致                | 影响写入可靠性                         |
| 成本模型     | Serverless 按量 vs 自建集群       | 影响运营成本                           |

存储接口返回成功，只能说明写入完成，内容是否正确还得另查。比如 JSON Schema 能检查必填字段和类型，却不能证明“可能升级”已经变成“决定升级”。重要记录保留源消息和抽取结果，低置信度记录留待复查，才有机会发现这种误写。

### 主流 Memory 产品如何对比？

选 Memory 产品时，可以先看已有系统缺哪部分：缺少对话事实的抽取和检索，可以考察 Mem0；主要受长对话窗口限制，可以看 LETTA 的上下文管理；查询经常涉及人物、项目和时间关系，再看 ZEP 等图记忆方案。表中列出各自的侧重点，不能据此省略延迟、数据形态和合规要求的核对。

| 产品                                   | 核心思想                            | 技术亮点                                                                                                           | 适用场景         |
| -------------------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------- |
| [Mem0](https://github.com/mem0ai/mem0) | 单次 ADD-only 抽取 + 多信号融合检索 | 单次 LLM 事实抽取，后续去重并建立实体链接；检索融合语义、BM25、实体等信号；可选 GraphStore 后端支持图记忆（Mem0g） | 通用对话记忆     |
| LETTA（原 MemGPT）                     | 操作系统虚拟内存分页                | Main Context ↔ External Context 动态交换；递归摘要压缩                                                            | 长对话上下文管理 |
| ZEP                                    | 时间感知知识图谱                    | 自研 Graphiti 引擎；情景/语义/社区三层子图；边失效机制                                                             | 企业级多租户场景 |
| A-MEM                                  | Zettelkasten 知识管理               | 卡片笔记法；记忆间自动建立语义连接                                                                                 | 知识密集型任务   |
| MemOS                                  | 异构记忆的统一管理                  | MemCube 统一描述纯文本、激活和参数记忆                                                                             | 全栈记忆管理     |
| MIRIX                                  | 六模块分工协作                      | 元记忆管理器路由；不同记忆组件采用不同存储结构                                                                     | 复杂决策支持     |

Mem0 这一行参考其[官方架构说明](https://docs.mem0.ai/core-concepts/memory-evaluation#architecture-overview)。其中“单次”指事实抽取，不能理解为抽取、实体链接和后续处理都在一次 LLM 调用中完成。托管平台与开源 SDK 的能力也要分别核对。

### LETTA、ZEP、MemOS 有什么不同？

LETTA 的前身 [MemGPT](https://arxiv.org/abs/2310.08560) 借鉴了操作系统的内存层级：Main Context 放模型当前可见的内容，External Context 保存窗口之外的信息，需要时再检索回来。对话历史过长时，摘要可以压缩占用，但摘要不会保留所有细节。比如原始报错栈或精确数值只剩下概括，后续排查就可能需要重新读取原始记录。

ZEP 更关注带时间的事实关系。例如，项目何时切换到 Java 21，与系统何时收到这条消息，可能是两个时间。[官方 Facts 文档](https://help.getzep.com/v4/facts)用 `valid_at`、`invalid_at` 表示推断出的事实有效期，用 `created_at`、`expired_at` 记录系统的创建和失效处理时间。旧事实可以保留，用于回答历史问题。这里仍要核对内容是否真的矛盾；两个时间段重叠，不代表其中一条记录就必然错误。

[MemOS 论文](https://arxiv.org/abs/2505.22101)尝试统一管理三种记忆：纯文本、激活和参数。前面提到的 KV Cache 属于激活记忆，LoRA 则是参数记忆的一种实现。它们对模型和运行时的要求不同，采用哪一种形式，需要具体的转换和使用策略。

如果用户偏好经常改变，还需要按条删除，外部文本或数据库记录更便于维护。内容一旦进入模型参数，删除原始记录就无法同步消除其影响，可能还要重训、替换适配器或采用机器遗忘方法。多租户使用独立 LoRA 适配器时，也需要运行时支持相应的加载、隔离和卸载。

MemCube 管理的对象可以概括为：

```text
MemCube：统一描述和管理异构记忆
├── 纯文本记忆：文本、结构化记录
├── 激活记忆：KV Cache 等运行时表示
└── 参数记忆：LoRA 等参数化形式
```

## 记忆的高级演化机制有哪些？

同一偏好写入五次，查询时可能五条都被取回。它们占用了候选位置，实际却只提供一份信息。记忆维护要处理的就是这类重复记录，以及已经过时、互相矛盾的内容。

![记忆系统的高级演化机制](https://oss.javaguide.cn/github/javaguide/ai/agent/agent-memory-evolution.png)

### 记忆反思与合成如何实现？

**合并与反思的区别，在于有没有产生新的判断。** 合并同一项目的重复背景，可以保留一份内容和多个来源；反思则会从已有经历中归纳后续可用的做法。

[Generative Agents](https://arxiv.org/html/2304.03442v2#S4.SS2)会把归纳出的较高层次结论重新存入记忆。代码审查也可以采用类似思路：多次反馈都要求优先处理 OOM 风险，就把它整理成后续审查的检查顺序。

归纳结果需要附上来源和适用范围。只出现过一次 OOM 反馈，就认定用户始终把内存问题放在第一位，依据还不够；后续出现相反反馈，也应允许修改原来的判断。

高风险任务还可以在写入前加一道校验：证据是否齐全，验收条件是否满足？缺少的部分退回执行节点补齐。遇到互相矛盾的记录，则先核对时间和来源，不要让摘要把矛盾掩盖掉。额外检查会增加模型调用和等待时间，是否采用要看任务风险。

### 记忆的清理与遗忘机制是怎样的？

用户去年使用 Java 8，今年明确切换到 Java 21，后续回答就不应继续套用旧版本。系统可以将旧记录标记为失效，保留历史来源；检索当前偏好时排除失效项。

对于仍然有效的记录，还可以结合相关性、重要性和时间因素排序。例如，采用乘法衰减时可写成：

```text
score = relevance × importance × decay(t)
```

其中 `decay(t)` 可以取 `e^{-λt}`。这是一种可选策略，**不是《Generative Agents》的原公式**。该论文先归一化 recency、importance、relevance，再加权求和，实验中三项权重均为 1，见[论文的检索部分](https://arxiv.org/html/2304.03442v2#S4.SS1)。选择加法还是乘法会影响某一项较低时的排序，需用实际查询评估。

记录多时，可以先召回一批候选，再计算时间分数。不过，如果第一步没有取回一条重要记忆，后续重排再精细也用不上它。评测时需要同时观察候选数量和最终结果。

Java 8 的旧偏好标记为失效后，磁盘空间可能还没有释放。检索层先按状态和时间排除它，数据库再按自身的删除、压缩机制回收空间。这是两件不同的事；是否重建索引、怎样清理，也要看具体产品，不能把所有 HNSW 实现都当成需要手动执行 Vacuum。

## 如何优化长期记忆的检索效果？

向量相似度能找出语义接近的记录，但版本号、项目名和用户范围还需要另外处理。

![长期记忆的检索优化策略](https://oss.javaguide.cn/github/javaguide/ai/agent/agent-memory-retrieval-optimization.png)

### 混合检索与元数据过滤怎么做？

查“Java 21 升级记录”，我们希望找到的是这个版本的升级过程。向量检索可能返回 Java 8 的迁移讨论，因为它们谈的都是升级；只用关键词，又可能漏掉没有写出“升级”二字的相关记录。

混合检索（Hybrid Search）会把两路结果结合起来：BM25 / Sparse 补充版本号等精确词的匹配，Dense 补充语义相近的记录。于是同一条升级记录可能出现在两份结果里，而且分数不同。此时要决定怎样合并，而不是直接拿两个原始分数比大小。

**RRF（Reciprocal Rank Fusion）使用排名计算融合分数。** 对同一条记录，分别取它在两份结果中的位次，再合并贡献。两路分数的尺度不同不会直接影响这一步，但各路召回多少条、融合参数怎样设置，仍会影响结果。

想直接使用分数，可以采用线性加权 `α·dense + (1-α)·sparse`。前提是先处理两路分数的尺度差异，否则权重相同也不代表贡献接近。`α` 可以用标注数据校准；版本号查询和模糊意图查询依赖的信号不同，不一定适合同一个权重。

也可以把两路候选合并去重，交给 **Cross-encoder Reranker** 重新评分。Reranker 会比较问题与每条候选，不再只是合并原有排名。不过它多出一轮计算，是否值得采用，要在实际查询集上比较，长尾 query 也应单独观察。

融合之前还要保证候选的访问范围正确。UserID 和组织 ID 等隔离条件应由数据访问层注入，不能指望模型每次调用工具都自行填对。项目、时间范围和业务标签则按任务需要附加。

过滤后的查询也要进入评测集。一条记录在全库里排得很靠前，却可能根本不属于当前租户；数据库执行检索时怎样结合过滤，也会影响耗时，具体可参考 [Qdrant 的过滤说明](https://qdrant.tech/documentation/search-design/vector-search-filtering/)。需要独立硬件或进程隔离时，还得在部署层安排，划分 Collection 不能替代这一步。

### 为什么检索链路优化往往先于写入策略？

发现回答仍在使用 Java 8 配置时，可以拿着这次请求的 Trace，逐步核对 Java 21 升级记录。要找的是它第一次出错或丢失的位置：

1. **看源消息和记忆记录。** 用户说“准备升级”，记录却写成“已经升级”，需要修正抽取或写入。检索再准确，也无法保证模型依据这条错误记录答对。
2. **看候选列表。** 记录内容正确，却不在候选中，检查项目 ID 等过滤条件和召回过程。
3. **看最终请求。** 候选中有记录，请求中没有，继续查重排和上下文裁剪。信息可能在这些步骤被排除。
4. **看回答如何使用证据。** 请求里已经包含正确的 Java 21 记录，仍使用 Java 8 配置，就检查其他上下文是否冲突，以及模型是否忽略了正确依据。

源记录缺失或抽取错误，才需要回到写入过程处理。记录本身正确时，就沿 Trace 找它在哪里被排除。改完用原查询重跑，一次核对记录去向，一次核对回答，避免只看到答案变化就认定故障已修复。

做方案对比也要固定查询集、检索次数和预算。例如，[Mem0 官方基准页](https://docs.mem0.ai/core-concepts/memory-evaluation)（2026-11-08 核对）以单次检索、`top_200` 为预算，报告的 Overall 分数是：

- LoCoMo：92.5。
- LongMemEval：94.4。
- BEAM (1M)：64.1。

同一组结果还记录了上下文用量：平均检索上下文不足 7K Token，对比的全上下文方案通常使用 25K+ Token。这些数字应和回答质量一起比较；若一个方案取回更多材料，也可能只是用了更大的预算。

这里测试的是 Mem0 托管平台，其中有开源 SDK 不具备的专有优化。自行部署时可以参考测试口径，不能直接把这组分数作为自有系统的结果。

## 生产级记忆系统架构要关注哪些要点？

用户改了报告格式，数据库已经保存新值，回答却仍按旧格式生成，问题可能出在 Redis 缓存。Trace 里应能看出这次请求读取了缓存还是源记录，否则只检查数据库，很容易漏掉旧副本。

索引和缓存解决不同的查询需求，隐私保护则贯穿写入和后续使用：

| 维度     | 核心问题    | 解决方案                              |
| -------- | ----------- | ------------------------------------- |
| 多维索引 | 召回精度    | Vector + Graph + Keyword 三种索引结合 |
| 隐私合规 | GDPR 等法规 | 写入前做 PII 脱敏                     |
| 冷热分离 | 性能与成本  | 高频偏好缓存 + 低频背景 RAG           |

Vector、Graph 和 Keyword 按查询需要选择即可。多加一份索引或缓存，就多一份要跟随源记录更新、失效和删除的数据；这些操作应能关联到同一条记忆，方便核对各处是否一致。表中的 PII 脱敏只是一项隐私保护措施，不能单独证明法规合规。

## 如何用 Markdown 存储 Agent 记忆？

项目已经有明确的测试命令和接口约定时，把它们写进 Markdown，Agent 读文件就能获得这些信息。例如 `mvn test`、接口返回统一使用 `Result<T>`，都不需要先经过一次向量检索。

### 为什么 Markdown 可以作为 Agent 记忆？

以测试命令为例，写进文件之后，退出 Agent 并不会删除它。下次启动时，宿主可以把文件内容送进上下文；只对某个目录有效的约定，也可以在处理该目录时读取。

团队将规则纳入 Git 后，测试命令怎样变过、为什么修改，都有版本记录可查。个人偏好则另外保存，避免随团队规则一起提交。

这也说明了文件迁移的限制：Git、同步盘或共享存储能把内容带到另一台机器，却不能决定新的 Agent 是否读取它。换工具时，仍需按新宿主的规则安排文件名、目录和加载时机。

Manus 使用文件系统保存外部记忆；Claude Code 则提供 `CLAUDE.md` 和 Auto Memory。少量项目约定采用这种方式，可以省去独立检索服务，但文件维护、读取和上下文占用仍有成本。大量自由文本不宜每次全量加载，需要另加检索来筛选。

### Claude Code 的 `CLAUDE.md` 机制是怎样的？

Claude Code 的记忆系统采用双轨制：人工编写的 `CLAUDE.md`，以及自动积累的 Auto Memory。

#### `CLAUDE.md` 里该写什么、不该写什么？

官方建议每个 `CLAUDE.md` 尽量少于 200 行，这是控制上下文开销的建议，并非超过 200 行就不读取的硬限制。通过 `@` 引用拆分文件可以改善可维护性，但已加载规则的引用内容仍会进入上下文，不能把拆文件等同于减少 Token。只针对部分目录的规则可以拆到 `.claude/rules/`，通过 `paths` 配置限定加载范围，具体触发方式见下文。

订单项目使用哪个 Spring Boot 版本、怎样启动测试、SQL 审计依赖什么约定，都可以写进 `CLAUDE.md`。这些信息会影响具体改动；“代码要高质量”没有说明判断标准，写进去也无法替代检查。测试、lint 和启动命令直接给出可执行形式，便于运行后核对结果。

规则需要说明适用对象和原因。例如项目确实依赖 QueryWrapper 解析 SQL 审计日志，就应把这项依赖写在查询规范旁边，避免 Agent 将它当成可以随意替换的代码风格。提交格式、分支命名和环境变量约定同样应与项目实际配置一致。

格式化工具已经强制执行的规则，无需再写成长篇说明。参考资料可保留入口，让 Agent 在相关任务中读取。

#### 怎么写才能让 Claude 真正遵守？

“注意依赖注入规范”没有说明改动应该是什么样。若项目禁止字段注入，可以直接指定构造器注入，并给出已有实现的位置：

```markdown
# 依赖注入

- 不要使用 @Autowired 字段注入
- 使用构造器注入，配合 Lombok 的 @RequiredArgsConstructor
- 参考示例：UserController.java 中的写法
```

保存规则后，先确认文件被加载，再检查它是否与其他规则冲突。`IMPORTANT:`、`YOU MUST:` 之类标记不能代替这两步，也不能保证模型遵守。可以用一次相关改动验证规则是否起作用；可机械检查的要求则交给 lint 或测试执行。

标题可按 Commands、Structure、Conventions、Testing 等用途组织，便于定位命令和约定。

#### `CLAUDE.md` 文件的层级结构是怎样的？

| 层级   | 位置                                      | 作用范围     | 适用场景                                                                        |
| ------ | ----------------------------------------- | ------------ | ------------------------------------------------------------------------------- |
| 组织级 | 系统目录，如 `/etc/claude-code/CLAUDE.md` | 所有用户     | 公司指导性规则；不能用 `claudeMdExcludes` 排除，强制限制应使用 managed settings |
| 用户级 | `~/.claude/CLAUDE.md`                     | 个人所有项目 | 代码风格偏好、个人工具习惯                                                      |
| 项目级 | `./CLAUDE.md` 或 `./.claude/CLAUDE.md`    | 团队共享     | 项目架构、编码标准、工作流，提交至 Git                                          |
| 本地级 | `./CLAUDE.local.md`                       | 个人当前项目 | 沙箱 URL、测试数据偏好，需手动加入 `.gitignore`，运行 `/init` 可自动添加        |

文件加载会从当前工作目录向上查找祖先目录，子目录规则则在处理相应文件时按需读取。同一目录内，`CLAUDE.local.md` 追加在 `CLAUDE.md` 之后，但加载顺序不等于程序配置中的确定性覆盖。规则互相矛盾时，应直接消除冲突，不能依赖模型总是选择更近的文件。

`CLAUDE.md` 不适合存大段日志和完整对话记录，也不应该存敏感密钥、Token、账号信息。高频变化的运行时数据、可以实时查询的动态信息，也不适合写进去。

构建命令和通用约定可以留在项目根目录；API、数据库等细节单独维护，再从根文件引用。比如订单项目可以这样组织：

```markdown
# `CLAUDE.md`（项目根目录）

## Project

Spring Boot 3.2 + MyBatis-Plus + MySQL 8.0 的订单管理服务。

## Commands

- 构建：`mvn clean package`
- 测试：`mvn test`

## Rules

- API 约定：@docs/api-conventions.md
- 数据库规范：@docs/database-rules.md
```

这里的 `@path/to/file` 会导入目标文件，最多支持 5 层递归。[官方文档](https://code.claude.com/docs/en/memory#import-additional-files)规定，项目级记忆引用工作目录外的文件时，首次需要批准；拒绝后，该项目的外部导入保持禁用，也不会再次弹出同一对话框。

引用跟着所属规则文件加载：根规则在启动时读取，其中的引用也会展开；子目录规则按需读取时，才展开相应引用。因此，拆文件方便维护，但已加载的文字仍然占用上下文。

如果一条规则只针对 Controller，放进所有任务都会加载的文件中就没有必要。可以在 `.claude/rules/` 下用 `paths` 限定它的范围。[官方文档](https://code.claude.com/docs/en/memory#path-specific-rules)说明，读取、写入或编辑匹配文件时会加载这类规则，部分可识别的 Bash 读取命令也会触发；没有 `paths` 的规则则在启动时加载。

```yaml
---
paths:
  - "src/main/java/**/controller/**/*.java"
---
# Controller 规范
- 统一使用 Result<T> 包装返回值
- 所有接口必须添加 Swagger 注解
```

处理 Controller 文件时，上面的路径模式会匹配；只处理 Service 文件时，不会因为这个模式加载 Controller 规则。不过，已经读入的规则不会在切换文件后自动消失，所以正文也要写清“Controller 规范”的适用对象。

#### AGENTS.md 和 CLAUDE.md 是什么关系？

几种编码 Agent 共用一份项目约定时，可以把它写在 `AGENTS.md` 中。按 2026-11-08 核对的[官方文档](https://code.claude.com/docs/en/memory#agentsmd)，Claude Code 从 v2.1.277 起支持直接读取它。

不过，默认加载有条件：当前工作目录及其祖先目录没有 `CLAUDE.md` 或 `CLAUDE.local.md`。Project instructions 设置和内置插件是否启用，也会影响这条加载路径。因此，文件存在并不代表当前会话已经读取。

旧版 Claude Code、不支持直接加载的会话，或者还要保留 Claude 专属规则的项目，可以继续从 `CLAUDE.md` 导入共享文件：

```markdown
@AGENTS.md

## Claude Code 特定指令

- 使用 plan mode 处理 `src/billing/` 下的改动
```

#### Auto Memory 是什么？

Auto Memory 保存 Claude 在工作中选出的笔记，例如用户反馈、项目背景或以后可能用到的资料入口。`CLAUDE.md` 则由人维护明确的规则，两者可以同时使用。Auto Memory 从 [Claude Code v2.1.59](https://github.com/anthropics/claude-code/releases/tag/v2.1.59) 开始提供，按[官方说明](https://code.claude.com/docs/en/memory#enable-or-disable-auto-memory)，本地会话默认开启。

运行 `/memory` 可以查看和修改笔记，也可以直接检查默认目录 `~/.claude/projects/<project>/memory/`。同一仓库的 worktree 和子目录共用这份数据；它保存在本机，不会自动出现在另一台机器上。

[官方文档](https://code.claude.com/docs/en/memory#auto-memory)把笔记分为用户、反馈、项目和外部资料入口四类。不是每次对话都会新增笔记：Claude 会选择它认为值得保留的信息，代码和 Git 历史中能直接查到的内容不应再重复保存。

真正进入启动上下文的是 `MEMORY.md` 索引的前 200 行或前 25KB，以先达到的限制为准。详细笔记由索引指向 Topic 文件，使用时再读取。因此，重要入口要放进索引的有效范围。这里与 `CLAUDE.md` 的“尽量少于 200 行”不同，后者只是建议，不是读取上限。

发现 Claude 仍沿用旧偏好，应修改对应记忆文件。删除会话记录不会连带清理这份数据。需要集中整理笔记时，社区 dream-skill 提供 Orient、Gather Signal、Consolidate、Prune 四阶段处理方式，但它不属于官方功能。

CI/CD 中不需要积累临时笔记时，可以设置 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`。另外两个关闭入口是 `/memory` 和 `autoMemoryEnabled` 配置。

### Markdown 记忆如何分层设计？

前面列出了 Claude Code 的加载层级，实际放文件时，还需要分清“谁来维护”和“谁会用到”。

个人在所有项目中都希望使用 2-space 缩进、先写测试或不用 emoji，可以记到 `~/.claude/CLAUDE.md`。当前团队的技术栈和测试命令则放在仓库根目录 `CLAUDE.md`，随 Git 共享，避免每个人各存一份不同版本。

局部规范跟着目录走：`backend/` 的 API 约定放在对应子目录，`docs/` 的写作要求也放在自己的范围内。需要按文件模式加载时，可以用 `.claude/rules/`。个人当前项目的工作流放入 `CLAUDE.local.md`，并加入 `.gitignore`。

团队共享和个人私有，是在这些文件位置上决定是否提交。它们不需要再各自建立一套相同的项目规则。

### Markdown 记忆和传统长期记忆的边界在哪里？

![Markdown 记忆和传统长期记忆的适用边界](https://oss.javaguide.cn/github/javaguide/ai/agent/agent-memory-markdown-memory-boundary.svg)

少量规则可以直接读文件，大量历史记录往往需要先检索。表中的几种方案可以组合使用，其中 RAG 是处理流程，Mem0 等是记忆管理框架，并不都属于存储介质。

| 维度       | Markdown 记忆                                | 向量库记忆                           | RAG 知识库                     | 记忆管理框架（Mem0 等）            |
| ---------- | -------------------------------------------- | ------------------------------------ | ------------------------------ | ---------------------------------- |
| 检索方式   | 依赖宿主，可全量加载、按路径读取或另接检索   | 向量检索，可结合过滤与混合检索       | 由检索、重排和证据筛选流程决定 | 由配置的存储、检索与记忆策略决定   |
| 上下文成本 | 取决于实际加载内容，大文件全量注入会挤占空间 | 取决于返回条数和片段长度             | 取决于检索预算与上下文组装     | 取决于记忆检索和注入策略           |
| 调试体验   | 可直接检查文件及加载记录                     | 需检查候选、过滤与排序               | 需追踪检索到生成的链路         | 需同时理解抽取、存储和检索逻辑     |
| 部署成本   | 少量文件可直接读写，大规模时仍需索引         | 可选嵌入式、自建或托管服务           | 需要编排检索与生成组件         | 取决于框架、存储及模型调用方式     |
| 版本控制   | 可纳入 Git                                   | 文本、向量与索引版本需协调           | 语料、索引和配置需同步管理     | 记忆数据、规则和框架版本需协调     |
| 迁移成本   | 文本易迁移，需适配加载规则                   | 取决于数据导出、向量兼容性和索引重建 | 取决于语料、索引和流程适配     | 取决于数据格式、存储后端和接口适配 |
| 适用场景   | 偏好、约定、踩坑记录                         | 多样化记忆检索                       | 共享知识查询                   | 复杂多源记忆管理                   |

同一批问题分别交给这些方案，才能比较检索精度、回答依据、延迟和成本。表中的存储和维护方式，不代表检索效果的高低。

项目编码规范通常可以直接指定文件。查询“上次为什么没有升级 Java 21”时，相关讨论可能散落在多份历史记录里，就需要关键词或向量检索定位。即使原文保存在 Markdown 中，也可以另外建立索引。

这两类内容可以分别读取：约定从固定入口加载，历史材料先检索再加载。

### Markdown 记忆应如何维护？

修改项目测试命令时，顺便检查 `CLAUDE.md` 是否还引用旧命令。文件和代码一起维护，比等 Agent 执行失败后再补规则更直接。`/init` 生成的文件也要核对项目描述和命令，不能因为是工具生成的就跳过审查。

用户纠正一次行为后，可以先保留原话和任务背景，再判断要不要写成长期规则。“这次使用某种报告格式”只约束当前任务；已经确定的团队要求则可以直接写入。临时要求全部长期保存，后面反而需要不断解释例外。

整理已有规则时，重复要求可以合并，但适用对象不能丢。比如只约束 Controller 的返回格式，移到局部 rules 文件后仍要写明 Controller，不能缩成“所有方法都返回 `Result<T>`”。拆分后再检查对应任务是否加载了规则；其他冲突的处理，见前面的“怎么写才能让 Claude 真正遵守”一节。

准备删除一条规则，可以先问 Claude 它是否有用，但这个回答不够作为删除依据。保留旧版本，用确实涉及该要求的任务对照检查，才能看到行为有没有改变。少数任务没有变化，也只能说明这些任务没暴露差异。

团队共享规则通过 Git 和 PR 维护，增删理由留在评审里。删错或改错时，可以据此恢复旧版本。

## 排查记忆问题时先看检索 Trace

Trace 至少要能串起原始消息、抽取记录、实际过滤条件、候选列表和最终上下文。用同一条记录去核对这些位置，方法见前面的 [Java 21 排障过程](#为什么检索链路优化往往先于写入策略)。

只看最终回答，很难分清是没存、没查到，还是查到了没有使用。Trace 应能关联到具体记录；否则即使更换模型或调大召回数量，也无法确认解决的是哪个问题。

## 总结

当前任务进度放在会话状态中，跨会话仍有价值的偏好和决策另行保存。对项目编码规范这类少量信息，Markdown 已经可以满足基本需求；历史记录积累多了，再根据查询方式增加索引和检索。保存以后，还要留出更新、纠错和删除的入口。
